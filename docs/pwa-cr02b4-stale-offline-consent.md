# PWA CR02b4 · Cancel stale offline write intents after account/purge changes

Part of #2348 P0-04: the authorized P1 opt-in/metadata store was already bounded and each capture verified durable consent inside its IndexedDB transaction, but a prior **enable-consent intent** could wait for `indexedDB.open` while a logout cleared the store, then reopen the same scope afterward. That is distinct from a stale server GET and from an OS quota fault.

This scoped production change adds a process-local invalidation epoch incremented **before** origin-wide clear, account opt-out, or a mounted peer BroadcastChannel purge. New consent and per-Owner directory/album capture operations snapshot that generation at the start and recheck it after database opening and inside asynchronous IDB callbacks, including the nested relaunch-hint query. After invalidation, earlier operations cannot write a fresh consent or stale item summary; only a new user-intended opt-in can start under the new generation. Existing transaction-level persisted consent and Owner/instance/Origin isolation stay mandatory; public SW remains public-only, no new private cache.

A deterministic Node test delivers delayed IDB `open().onsuccess` **after** the clear operation has committed, and delivers another peer purge while an opt-in is still waiting. Both cases require zero late owner/hint writes. The fake database is just a scheduler for this specific race; it is **not** native Chromium quota or a claim about all Browser lifecycle interleavings. Real multi-Owner Go ACL stays covered by #2349/#2378; further real suspended HTTP/AbortSignal cross-tab integration is still OPEN #2348.
