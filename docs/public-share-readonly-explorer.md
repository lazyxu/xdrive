# Public capability read-only FileExplorer view (2026-10-19)

## Architecture choice and scope

The original `ui/shared/src/mui/FileExplorer.tsx` is a **7300-line account-owned interaction controller** containing clipboard, paste/cut/copy/move/delete/rename/upload, app tabs, drag, search, persistence, selection and owner-only data sources. It is **not safe to instantiate the full component with `readOnly=true` and a public capability token**: hiding buttons does not create a security boundary, and private mutation keyboard/context/drag paths remain coupled to Owner APIs.

Instead, create the small shared **`XDrivePublicShareReadOnlyExplorer` presentation** and lift the existing `XDriveFileExplorerItemIcon`, `xDriveFileKind`, `xDriveFileTypeLabel` and `xDriveFileSupportsThumbnail` unchanged into `FileExplorerItemPresentation.tsx`. The authenticated full FileExplorer re-exports those identical helpers. The public component imports only the new pure display leaf; it never imports the full account shell or accepts an `XDriveApi`, a session, a private Node object, a mutation callback or an owner data source. Shared visual semantics are identical; no duplicate full virtualizers or icon classification.

The recipient route remains `#/s/<token>` → `PublicShareView` → public-only `XDriveApi.publicShare`, `publicShareChildren` (POST token+optional password, cursor) and `downloadPublicShare` signed descendant tickets. The server remains authority for all scope, expiry, revoke, password, download allowance, ancestor and current revision checks. No public download causes a recursive ZIP or directory sync.

- **Single-file share**: same shared read-only Explorer item/icon/type/size presentation with exactly one original native Download submit button; no fictitious child folder or general private preview route.
- **Folder share**: default Details/List, optional Grid on same one received 100-item page, logical file type icons, nested breadcrumbs, Enter/double-click and explicit Open/Download, previous/next keyset page. Old accepted rows/crumbs and minimum 180px region remain on slow/failed/superseded reads; no ephemeral loading overlay. This is NOT an OS network drive, WebDAV/SMB mount, Owner FileExplorer, unauthorized thumbnail video playback or 100k DOM snapshot.
- Every page has `<=100` items; no new background thumbnail/media requests, no search over retained first 100 pretending to cover entire folder. Browser tab-hidden, superseded navigation and unmount retain existing AbortController→HTTP→Go Request.Context cancellation; user native signed downloads stay task-owned.
