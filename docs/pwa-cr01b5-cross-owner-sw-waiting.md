# xDrive PWA CR01b5 · Distinct Owners upload concurrently during SW waiting

Date: 2026-10-22. Parent issue #2347 (P0-07).

This is a strictly opt-in new mode of the already merged CR01b3 real browser/Go/Caddy/PG17/LocalCAS fixture; it does NOT duplicate the entire runner. The test creates a second normal-role user through the original authenticated Go admin user API. It uses **two separate Chromium BrowserContexts**, each with independent auth storage, an old active Service Worker and unchanged DOM/controller. Two distinct HTTP/2 streaming PUTs have separate UploadSession identifiers and two physically distinct unfinished temporary CAS files when the new Web build is published. Each browser's own worker must be stably waiting. Both streams are released only after this witness, and independent SQL + full physical 17 MiB and 6 MiB CAS/SHA postflights verify their owners remain distinct.

Cross-account security is proven through live Go HTTP: account A GET of account B's resulting Node and UploadSession must both be 404; account B GET of A's equivalents must both be 404. The second physical postflight must identify a normal user distinct from the original A administrator. Both new Service Workers may activate only after the respective old browser clients close. Original same-account CR01b3 mode is unchanged and is run in the same Node source-contract gate.

**Boundary**: Independent browser contexts have independent SW registrations; this is deliberate because two accounts cannot safely share a mutable localStorage session. The test is not a claim that one SW registration simultaneously contains two different logged-in accounts. The production Files picker, cross-browser OS installed behavior and Server Durable Task overlap remain separate tasks. Do not archive browser profiles, JWT, user names, private Go logs, CAS data or HAR. Do not cache private content through SW or auto-delete historic public assets. Require exact-head dedicated Chrome/Caddy/Go/PG17 specialty and complete cross-platform CI/Final Gate, then merge only after fresh clean. Inaccessible production-only security acceptance is 按用户决定跳过（未验收）, but code-level Owner/ACL/negative CI remains mandatory.
