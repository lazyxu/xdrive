# Folder share right-click parity (2026-10-19)

The merged folder capability sharing API (#2031) accepts either an owner File or a non-root Directory Node; both Web and Desktop pass onShare for each kind. The original shared FileExplorerActions menu factory only added the Share item in the file branch. This fix makes Share a common item while preserving file-only History and prior file action ordering. Mobile Web consumes the same getItemMenuItems callback, rendering Share as "分享链接". A real compiled TSX factory regression test now exercises each kind and its callback.

Feature comparison: both kinds offer create/list/revoke, password, expiry, total-download limit, one-time raw token display and a common dialog. The file public page downloads its single original. The folder page browses only one 100-entry keyset page at a time and issues signed tickets to download individual descendant files; the folder download allowance is the aggregate number of descendant file tickets. Neither kind delegates writes or edits existing share credentials; the Owner root is never sharable. Mobile Web raw-file OS sharing is intentionally separate and only for small individual files, whereas folder native sharing should share the link, not recursively ZIP a whole tree. Public-folder thumbnail/video previews, full-text search and automatic ZIP are future features requiring separate permission/performance acceptance, not safe parity omissions to silently enable.

No Server SQL/Go, Blob/CAS, HTTP flow, virtual scrolling or request cancellation changed. This O(1) menu correctness patch is not an optimization: AFTER/speedup N/A. Existing original 100k share benchmarks remain authoritative (SH-P001 100k metadata/1000 pages P50 16,699ms; SH-P005 actual physical JPEG Chromium original/download successful).
