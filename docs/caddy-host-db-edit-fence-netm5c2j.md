# NET-M5-C2-J · Caddy Host DB pending freezes administrator configuration edits

The preceding NET-M5-C2-I DB-only reservation bound one saved IP/domain HTTPS desired revision, one AliDNS revision, and fixed non-secret intent/nonce/plan/candidate SHA-256 digests into a persistent `pending-unapplied` row. That was insufficient: an administrator could still change either desired HTTPS ingress or AliDNS credentials after the pending transaction, invalidating the future operator-signed plan.

This phase closes that **known, bounded DB-side mutation gap** without granting Caddy Host Apply. All Caddy HTTPS save, desired-history rollback, and AliDNS rotate/clear code paths now check the same sticky reservation *inside their existing versioned PostgreSQL write transactions* and return sanitized HTTP 409 if it exists. Their normal admin authorization, transaction audit, local encrypted credentials, and old saved revisions remain unchanged.

**Cross-replica lock order is essential:** the private Host DB pending transaction locks saved HTTPS desired → optional AliDNS credential → fixed pending. An AliDNS mutation, even for the *first-ever* credential when no AliDNS row exists, now first locks the same HTTPS desired row, then the AliDNS row, then checks pending. Without this shared serialization point a missing AliDNS row could race an uncommitted pending reservation. HTTPS save/rollback already lock the HTTPS desired row first. A blocked edit must never write a new revision, ciphertext, or success audit.

Original real PostgreSQL isolated-schema tests reuse the accepted NET-M5-C2-I setup with TWO independent DB connection pools and authenticated administrator routes. After creation of one pending record they test HTTPS edit, HTTPS revision rollback and initial AliDNS write through separate Server instances; all return 409 with no state/audit/secret changes. Read-only HTTPS state still reports `apply_supported=false` and the reservation is not consumed.

**Not a production Host Apply:** no exposed staging route, no independent operator signature proof, no DB↔host atomic transaction, no AliDNS secret host delivery, no real Rescue, no watchdog, no actual Caddy restart, no positive/negative client login acceptance, and no immutable applied revision proof. A sticky pending row cannot be cleared by ordinary administrators and needs a future separately approved operator reconciliation/recovery workflow. Production remains `apply_supported=false` and `restricted-apply=blocked`. This phase does not enable a UI Apply button.
