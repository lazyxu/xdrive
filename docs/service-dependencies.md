# Admin service dependencies, Baidu AK and Caddy HTTPS staging

## Scope and status

**Status:** Shared Web/Desktop **系统依赖** page exposes 11 instance-wide dependency health contracts and real administrator controls for encrypted Baidu Server AK, GeoNames radius/reload/history/rollback, and Photo Intelligence automatic scheduling. Independent Pull Worker liveness is observable through expiring PostgreSQL heartbeats (P1-D1), and its bounded scheduling policy is administrator-controlled with safe task-boundary acknowledgement (merged P1-D2 #1300). Other dependencies remain deployment-owned or planned. It is **not** a Docker controller, Compose editor, arbitrary host-path editor, or general-purpose credentials service.

### Contract

- HTTP: `GET /api/v1/admin/services`, guarded by the existing authenticated `requireAdmin()` group.
- Response: `{ checked_at, services: [{ id, group, label, status, detail, version?, model? }] }`.
- States are intentionally distinct: `ready` means a real probe succeeded; `unavailable` means configured/expected but the probe failed; `disabled` means no analyzer/resolver is configured; `unknown` means a store implementation lacks a readiness probe; `planned` means integration or probing is not implemented.
- PostgreSQL checks `PingContext` with bounded deadline. Storage reuses `Store.Ready(ctx)` when implemented. Face, visual/OCR, and semantic analyzers call existing local `Info(ctx)` contracts, without exposing sockets, secrets, or raw errors. GeoNames reports the actually loaded resolver and version.
- The standalone background Pull Worker reports `ready` only with a fresh database heartbeat, `unavailable` for a recently expired heartbeat, and `unknown` when no worker has ever reported or the database read fails. Heartbeat health is not a statement that individual sync runs succeed. FFmpeg Media Worker can optionally probe real isolated executable health; media task processing remains `planned`. Baidu Server Static Map v2 is the **only supported map provider**: `disabled` without AK/opt-in; `unknown` (configured but not actively probed) when enabled; maps stay unavailable rather than rendering an alternate map. GeoNames label resolution is independent.
- Probes run on explicit page load/refresh, are bounded by a shared two-second context, and have no side effects. The page does not poll when hidden.
- Backend permission, not sidebar visibility, is the authority. Desktop forwards the existing session via Agent IPC; it does not send user credentials into the Renderer.

### Deployment/source of truth

- **Existing:** `server`, `worker`, `postgres`, `caddy`, optional `photo-face` profile. Analyzer sockets, model images, CPU/memory limits and unrelated secrets remain Compose/host config. The Baidu AK can be edited and hot-applied with encrypted storage. The separately encrypted administrator AliDNS ID/Secret is also editable, but is only staged for a future restricted Caddy apply; no Server credential form performs deployment writes.
- **GeoNames:** Existing `XD_PHOTO_PLACE_GEONAMES_DIR` points at the *container-visible* folder; the dedicated read-only host mount is tracked separately in PR #1189.
- **Media:** an operator-provisioned FFmpeg/FFprobe process may expose a private Unix Socket runtime readiness probe; the media job queue, transcode and preview tasks are not yet integrated.
- **Maps:** Gallery Places uses **Baidu Server Static Map API exclusively**; no offline SVG basemap, self-hosted/alternate tiles, or fallback map. If disabled/unavailable, show a visible unavailability state. GeoNames remains an independent optional offline place-*label* resolver, never a map provider. See `docs/baidu-map-server-api.md`.
- Runtime control and editable settings require distinct permission, persistent configuration, compatibility, and Host Manager safety contracts. Do not mount Docker socket into Server.

### Acceptance gates

1. A standard (no-profile) deployment still serves file operations, uploads, sync and Gallery unchanged.
2. Unauthenticated and nonadmin API calls are rejected; admin sees only safe fixed status fields.
3. A missing/unreachable analyzer is distinguishable from a disabled one; a missing or failed Baidu map shows an explicit unavailable state and never renders an alternate map. The planned worker never displays a false green status.
4. Web hash route, sidebar, desktop navigation and IPC path open the *shared* MUI page; account switch/unmount drops stale results.
5. Old Agent/Server returns an explicit unsupported/error message and does not silently show fictitious health.
6. Go unit tests, Web lint/typecheck, Desktop main/renderer typecheck, and scoped CI pass before merge.

### P1-CD3b2b: opt-in real AliDNS read permission verification (current phase)

Admin-only `POST /api/v1/admin/services/caddy/alidns/verify-read` accepts *only* the current desired HTTPS revision and encrypted credential revision. It does not accept a hostname, URL, DNS action, port, filesystem path, or credential from the browser. Enabling intent must already exist, with a validated ASCII FQDN and a decryptable pair. The server re-checks both revisions under PostgreSQL locks and **commits metadata-only audit before making any remote request**. Each Server instance serializes attempts and rate-limits successful dispatch to at most one request every 30 seconds. A failed audit or stale revision performs no cloud access.

The runtime sends exactly one bounded, signed **read-only** `DescribeSubDomainRecords` request for that saved FQDN using Alibaba Cloud's documented **ACS3-HMAC-SHA256** signing algorithm, HTTPS/TLS 1.2+, a fixed `dns.aliyuncs.com` host, a fresh random nonce, no redirects, no environment proxies and a 7-second timeout. It does not browse arbitrary hosts, follow redirects or request DNS write operations. Responses are size-limited to 16 KiB and validated for an explicit successful RPC envelope. Cloud response text, credentials, domain, signature, record data and request identifier are not returned to the client or written to audits. After the request, HTTPS and key revisions are checked again; an intervening save/rotation cannot make an old result look current.

An explicit shared Web/Desktop **核验 AliDNS 实际只读权限** action is available only after the local prerequisite preflight says the saved HTTPS enable intent is configuration-complete. The bounded response distinguishes `read_authorized`, `denied` and `unavailable`. **A successful read does not prove DNS TXT write permission, Caddy config effect, ACME certificate issuance, TLS handshake or public reachability**; `write_permission_verified=false`, `apply_supported=false` and `public_https_verified=false` always. The verification result is ephemeral; no polling or cached persistent green status. Server-only network and auth; per-user 同步文件夹 and credentials are excluded.

Acceptance: deterministic ACS3 signature-vector test, fixed request path/headers, admin vs member rejection, strict revision/audit before cloud contact, duplicate throttling, denied/malformed/oversized response, response/audit redaction, concurrent credential rotation rejecting stale success, Web/Desktop typed request bridge and shared MUI response rendering; exact-head CI required. This does not complete Host Manager secret delivery or genuine HTTPS activation. Future **P1-CD3b2c+** must add restricted reversible, no-lockout Host Manager apply with independent DNS TXT write checks and real revision-specific TLS evidence before offering an enable/disable/apply button.

### P1-CD3b2a: read-only Caddy HTTPS configuration prerequisite check (this phase)

The shared Web/Desktop administrator service page adds an explicit **预检配置（只读）** action backed by admin-only `GET /api/v1/admin/services/caddy/https/preflight`. It reads existing persisted desired HTTPS enable/domain/revision and the global AliDNS credential revision. For enable intent, the Server validates domain syntax and locally decrypts/authenticates the separately encrypted **complete pair**, discarding plaintext without returning or logging it. For disable intent, a saved disable revision requires **no AliDNS credentials**. An unset intent remains incomplete. The preflight is intentionally stateless and never writes an audit revision or any host file, invokes a Docker/Host Manager action, sends credentials over IPC, calls Alibaba Cloud, resolves arbitrary user-provided hostnames or performs a DNS/ACME request.

The result returns only fixed revision numbers and **seven safe checks**: desired revision, domain, local AliDNS decryption, trusted Host Manager heartbeat, existing internal HTTP ingress health, restricted-maintenance apply capability (**always blocked in this phase**), and public HTTPS reachability (**always unknown in this phase**). It may separately report the existing host's *local* certificate/hostname proof from a validated fixed loopback observation, but **that proof is not tied to the administrator's desired revision or staged credentials**. `configuration_complete` means only that the chosen local admin intent has the required fields and decryptable secrets; it is never proof of AliDNS API permission or of live/public HTTPS. `apply_supported=false`, and the UI has no host enable/disable/apply button. Missing, stale or malformed Host Manager status remains unknown, not green.

Cross-boundary code uses the existing Go Client → Desktop Agent authenticated IPC → Electron Main/Preload/Renderer contract and exactly the same shared MUI panel as Web. Old Server/Agent versions show explicit unsupported state and stale request completions cannot cross refresh/account scope. Tests cover admin vs nonadmin, enable/disable/unset, corrupted ciphertext/missing keyring, unavailable/healthy host, redacted credentials/domain, stable read-only API and no unsafe apply route; the full exact-head CI remains the merge gate.

**Still not implemented:** proof that AliDNS credentials have actual DNS-edit permission, secure host-secret delivery, audited Host Manager execution/preflight, reversible Caddy switch that protects the current access path, revision-specific effective-state checks, certificate issuance, public DNS, WAN and physical TLS reachability. Those are **CD3b2b+**, not a prerequisite status disguised as completed deployment.

### P1-CD2: localhost HTTPS handshake and certificate effectiveness

Building on P1-CD1, the Host Manager checks a configured HTTPS endpoint **only at 127.0.0.1:the fixed operator-configured HTTPS port** after its Docker Caddy healthcheck passes. The host HTTPS bind must be loopback-accessible (`0.0.0.0` or `127.0.0.1`); an interface-specific bind cannot be assessed through localhost and is reported unverified, not as a definitive broken public TLS endpoint. The hostname comes only from the operator-owned `XD_DOMAIN` and is allowed **solely for SNI and OpenSSL trusted certificate-chain plus `-verify_hostname` validation**. It must be a bounded plain ASCII FQDN; URL, shell flags, wildcard, local host path, invalid label, invalid TCP port and arbitrary external DNS/HTTP input are forbidden. The call is timeout-bounded, read-only, strips its raw output and publishes no hostname, credentials, certificate, host port, container information or raw errors.

The bounded Host Manager summary now includes whether a trusted local TLS check is implemented and `tls_state` (`disabled`, `verified`, `failed`, `unavailable`, `invalid-config`). A fresh, regular, size-bounded status file and separate heartbeat are mandatory; an old Host Manager with no TLS capability never claims local HTTPS ready. The admin Server reports the Caddy gateway as `ready` in an HTTPS deployment only when **both internal HTTP proxy health and actual loopback TLS chain/hostname verification pass**. If HTTPS verification fails, status is `unavailable` although HTTP remains healthy. If the TLS probe is unavailable/unsupported, status is `unknown`, never green from an `XD_DOMAIN` setting alone. HTTP mode retains its proven internal HTTP readiness. The shared Web/Desktop service row shows independent configuration-intent and actual local TLS verification chips. **A valid local TLS handshake is not proof of public DNS, WAN ingress, firewall reachability or external HTTPS accessibility**; the UI always says so.

This step adds **no** Caddy domain or credential edit, start/stop action, Docker access to Server, or destructive host change. A future separately gated configuration, safe apply and audited rollback must avoid Web lockout and interrupting durable transfers. Regression tests include real-command allowlist, forced bad TLS verification, invalid host/port, untrusted/old runner status, false-green prevention, and identical Web/Desktop UI. Physical public TLS validation remains a distinct acceptance gate.

### P1-B2c: automatic GeoNames radius reconciliation on each Server instance (merged #1267)
