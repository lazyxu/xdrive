# Admin service dependencies and secure Baidu AK configuration

## Scope and status

**Status:** Shared Web/Desktop **服务与依赖** page exposes 11 instance-wide dependency health contracts and real administrator controls for encrypted Baidu Server AK, GeoNames radius/reload/history/rollback, and Photo Intelligence automatic scheduling. Independent Pull Worker liveness is observable through expiring PostgreSQL heartbeats (P1-D1), and its bounded scheduling policy is administrator-controlled with safe task-boundary acknowledgement (merged P1-D2 #1300). Other dependencies remain deployment-owned or planned. It is **not** a Docker controller, Compose editor, arbitrary host-path editor, or general-purpose credentials service.

### Contract

- HTTP: `GET /api/v1/admin/services`, guarded by the existing authenticated `requireAdmin()` group.
- Response: `{ checked_at, services: [{ id, group, label, status, detail, version?, model? }] }`.
- States are intentionally distinct: `ready` means a real probe succeeded; `unavailable` means configured/expected but the probe failed; `disabled` means no analyzer/resolver is configured; `unknown` means a store implementation lacks a readiness probe; `planned` means integration or probing is not implemented.
- PostgreSQL checks `PingContext` with bounded deadline. Storage reuses `Store.Ready(ctx)` when implemented. Face, visual/OCR, and semantic analyzers call existing local `Info(ctx)` contracts, without exposing sockets, secrets, or raw errors. GeoNames reports the actually loaded resolver and version.
- The standalone background Pull Worker reports `ready` only with a fresh database heartbeat, `unavailable` for a recently expired heartbeat, and `unknown` when no worker has ever reported or the database read fails. Heartbeat health is not a statement that individual sync runs succeed. FFmpeg Media Worker can optionally probe real isolated executable health; media task processing remains `planned`. Baidu Server Static Map v2 is the **only supported map provider**: `disabled` without AK/opt-in; `unknown` (configured but not actively probed) when enabled; maps stay unavailable rather than rendering an alternate map. GeoNames label resolution is independent.
- Probes run on explicit page load/refresh, are bounded by a shared two-second context, and have no side effects. The page does not poll when hidden.
- Backend permission, not sidebar visibility, is the authority. Desktop forwards the existing session via Agent IPC; it does not send user credentials into the Renderer.

### Deployment/source of truth

- **Existing:** `server`, `worker`, `postgres`, `caddy`, optional `photo-face` profile. Analyzer sockets, model images, CPU/memory limits and unrelated secrets remain Compose/host config. The Baidu AK is the **only** credential editable here, saved encrypted in PostgreSQL and immediately applied without restart.
- **GeoNames:** Existing `XD_PHOTO_PLACE_GEONAMES_DIR` points at the *container-visible* folder; the dedicated read-only host mount is tracked separately in PR #1189.
- **Media:** an operator-provisioned FFmpeg/FFprobe process may expose a private Unix Socket runtime readiness probe; the media job queue, transcode and preview tasks are not yet integrated.
- **Maps:** Gallery Places uses **Baidu Server Static Map API exclusively**; no offline SVG basemap, self-hosted/alternate tiles, or fallback map. If disabled/unavailable, show a visible unavailability state. GeoNames remains an independent optional offline place-*label* resolver, never a map provider. See `docs/baidu-map-server-api.md`.
- Runtime control and editable settings require distinct permission, persistent configuration, compatibility, and Host Manager safety contracts. Do not mount Docker socket into Server.

### Acceptance gates

1. A standard (no-profile) deployment still serves file operations, uploads, sync and Gallery unchanged.
2. Unauthenticated and nonadmin API calls are rejected; admin sees only safe fixed status fields.
3. A missing/unreachable analyzer is distinguishable from a disabled one; a missing or failed Baidu map shows an explicit unavailable state and never renders an alternate map. The planned worker never displays a false green status.
4. Web hash route, sidebar, desktop navigation and IPC path open the *shared* MUI page; account switch/unmount drops stale results.
5. Old Agent/Server returns an explicit unsupported/error message and does not silently show fictitious health.
6. Go unit tests, Web lint/typecheck, Desktop main/renderer typecheck, and scoped CI pass before merge.

### P1-B2c: automatic GeoNames radius reconciliation on each Server instance (merged #1267)

### P1-D1: independent Pull Worker heartbeat status (merged #1289)

The standard Compose `worker` service already runs the server binary in standalone `worker` mode. Previously the admin page always reported its separate process status as `unknown`, even if the worker was healthy. This phase adds a narrow, real liveness contract without introducing remote restart or changing per-user Source settings:

- Server startup migrates `xd_source_worker_presence` before the worker starts (Compose depends on a healthy Server). A normal long-running worker publishes a random process-instance ID, current scan/poll intervals and maximum concurrency to PostgreSQL every five seconds, expiring after 20 seconds. The one-shot CLI mode does not register as a persistent worker.
- Publication runs independently of a long-running Pull cycle. A graceful exit expires the row immediately; a killed/disconnected process ages out via its lease. Old records are pruned when another Worker starts. Errors are logged without preventing the existing pull loop from running.
- Existing admin-only `GET /api/v1/admin/services` reads actual persisted heartbeats with its two-second request timeout. A fresh heartbeat yields `ready` with the number of live Pull Workers; a recently expired heartbeat yields `unavailable`; no reports or unreadable records yield `unknown`. Records older than a day do not imply a currently configured deployment.
- The shared Web/Desktop status row requires no independent UI/controller. No hostname, process ID, credentials, per-user Source name/path or raw database error is exposed. Server-internal background scheduler tasks are not conflated with the independent Pull Worker process. No Docker socket or arbitrary host control is added.
- This is **observability only**, not the final Baidu-style edit/validate/save/apply/rollback controller. Worker polling and concurrency are still deployment-owned, `config_mode=deployment` / `apply_mode=controlled-restart`. A follow-up must implement a restricted configuration owner, versioned desired/effective runtime policy and acknowledgement before enabling any editor. Media Worker/FFmpeg, Caddy, PostgreSQL and storage settings remain separate.

**Validation:** unit test for the exact missing/fresh/expired/retired statuses and PostgreSQL integration test for publisher upsert/expiry and admin reader. Require full exact-head PR CI before merging. No local full Go 1.25 / PostgreSQL suite is claimed in connector-only execution.


### P1-D2: audited Pull Worker runtime scheduling policy (implementation)

The independent Pull Worker now supports administrator-only, version-guarded desired scheduling settings: scan interval in seconds (60..604800), poll interval (10..3600), and per-process network concurrency (1..8). This is a global scheduling policy, **not** a per-user Sync Folder schedule, a Push permission, or a container resource controller.

- `GET/PUT /api/v1/admin/services/source-worker` and `GET .../revisions`, `POST .../rollback` persist immutable revisions (including a default revision-zero snapshot on first edit) with audit inside the same PostgreSQL transaction. Invalid/full-object inputs return 400, stale writes 409; historical rollback creates a new revision. The default shown before the first save is the **code default only**, never an assertion about deployed environment flags.
- Saving produces desired state, **not** activation. A running Pull Worker reads new saved revisions at startup and between completed Source batches (with ten-second idle checks), changes polling/scan intervals without interrupting work and swaps its own network scheduler only at a completed batch boundary if concurrency changes. `worker --once` retains its CLI/deployment flags; no media, Push or durable tasks are cancelled by an administrator update.
- The Worker heartbeat publishes its effective scheduling values and applied revision. The administrator endpoint aggregates only **fresh** Worker leases by values/revision; no process IDs, hostnames, per-user Source records, credentials or paths leave the Server. `applied` requires at least one live Worker and **all observed live instances** match desired revision and values. Failed Worker config reads leave last-good settings active.

Installing/restarting/upgrading container images, CPU/memory limits, storage, PostgreSQL, Caddy or FFmpeg Media Worker still needs a restricted deployment controller that this phase does not add. No Docker socket is exposed.

**Tests and delivery:** bound validation; real PostgreSQL revision/audit/rollback and worker acknowledgement; safe Worker scheduler rebuild; shared Web/Desktop port, Go Client, Desktop IPC and Electron transport; exact-head GitHub CI. ### P1-B3a: administrator-staged, immutable GeoNames dataset backups (implementation)

**Purpose:** add a real, controlled first step toward data-version management without pretending that file deployment, cluster distribution or rollback already exists. This feature is **snapshot staging**, not a replacement for the active GeoNames resolver and not a remote file-upload API.

- The operator configures `XD_GEONAMES_SNAPSHOT_DIR` on the **Server** to point to a distinct, persistent, writable directory. For the current Compose deployment a dedicated subdirectory under the existing mounted `/data` is suitable, provided its permissions are provisioned for `XD_SERVER_UID`. The default is empty/disabled. The ordinary trusted `XD_PHOTO_PLACE_GEONAMES_DIR` remains read-only, with source files provided by the deployment. The administrator cannot supply or modify filesystem paths from Web/Desktop.
- A shared Web/Desktop admin button calls `POST /api/v1/admin/services/geonames/dataset-snapshots` with the current optimistic radius revision and expected active resolver version. The existing `requireAdmin` group protects the route, and Desktop forwards its authenticated session via Agent IPC. Both fields are required; stale version or radius returns HTTP 409.
- The Server only copies `cities500.txt`, `admin1CodesASCII.txt` and `countryInfo.txt` from the trusted source mount, rejecting symbolic links, missing/nonregular/empty files and over-limit inputs; per-file caps are 128 / 16 / 2 MiB, total 146 MiB. It writes into a temporary private directory under the configured root, computes a content-addressed SHA-256 fingerprint independent of matching radius, and runs `LoadGeoNamesResolver` on that copied candidate before any publication.
- A complete, validated copy is renamed under its fingerprint. The immutable manifest in `xd_admin_geonames_dataset_snapshots` and a metadata-only administrator audit are committed together. If the database/audit operation fails, the new copy is cleaned up and the **active runtime and prior snapshots are unaffected**. Attempting to stage an existing content fingerprint fails safely with HTTP 409; it never overwrites an existing version. Request or validation failures never replace the in-memory resolver.
- The existing `GET /api/v1/admin/services/geonames` reports whether staging is configured, a bounded list of 20 recorded snapshots, their content fingerprints, verified radius/revision/byte totals and whether the snapshot directory exists **on the currently responding Server**. Directory presence is not a fresh hash audit or a claim that every replica holds the same files. Missing schema/old Server/Agent produces explicit unsupported feedback rather than a green action.
- The shared administrator UI labels every entry **已暂存、未应用**. No action is exposed for arbitrary host-path browsing, direct user-file upload, selecting an old data directory as active, mounting storage, restarting containers or downloading data from the network. In-flight PlaceRunner work, background synchronization, uploads and downloads remain untouched.
- Next phase **P1-B3b/B3c** must separately implement authenticated dataset upload/transfer (with streaming and quota), secure per-replica distribution, exact immutable version apply/acknowledgement and a rollback contract. An archived copy alone does not satisfy fleet-wide apply or restore.

**Acceptance:** Go bounded-copy/symlink and real PostgreSQL authorization/revision/audit/immutable-history regressions, shared Web/Desktop source contract, full Go/Windows/Web/Desktop CI and `final-gate`; production-volume test remains distinct and is not claimed from a CI success. GitLab is not changed through a GitHub-only connector.


### P1-B3b: verified, audited instance-local GeoNames dataset apply (implementation)

After P1-B3a made immutable dataset versions available, a current Server instance may **temporarily hot-apply a versioned, archived local dataset** (or restore the original read-only deployment data). This is an explicitly instance-local, *non-persistent* runtime action. Server restart loads `XD_PHOTO_PLACE_GEONAMES_DIR` as before; other replicas and their background work are not changed. Full desired-state persistence, cross-node transfer and coordinated application are later phases.

- Admin-only `POST /api/v1/admin/services/geonames/dataset-snapshots/apply` accepts only `revision`, `expected_version`, `expected_fingerprint` and a `target` equal to one exact lowercase 64-hex fingerprint or the literal `deployment`. No client path, bytes, shell command, Docker socket, arbitrary download or new per-user Source contract is accepted.
- The Server holds the existing GeoNames reload/save/rollback mutex, verifies active runtime version, radius revision and active dataset provenance, and fully validates the requested dataset before any runtime modification. Archived candidates must exist in the immutable PostgreSQL snapshot journal and the local private archive directory; the Server re-copies **bounded regular data files**, recalculates the radius-independent SHA-256 content address and checks recorded size, then builds the complete resolver from those exact private bytes at the *current desired radius*. Corrupt/missing/symlinked/oversized archives retain the last-good resolver; no claims are based on a directory-exists flag.
- After rechecking the revision, the Server records a metadata-only administrative apply audit **before** swapping the immutable `ReloadablePlaceResolver` pointer. In-flight PlaceRunner snapshots remain pinned. A later radius change, radius rollback, manual reload, or passive reconciliation on this same Server revalidates and rebuilds from the locally selected archived source, rather than silently jumping back to the original mount.
- `GET /api/v1/admin/services/geonames` exposes only `active_dataset_source` (`deployment` or `snapshot`), current snapshot fingerprint (empty for deployment), `active_dataset_persistent` (false only for temporary snapshot selection; true for the deployment default), and a truthful flag for whether the responding Server can validate archived versions. Web/Desktop share an explicit confirmation, target selector and success/error states. Existing replica heartbeat status remains observational, **not** an assertion that the entire deployment switched.
- The administrator may restore the trusted deployment data by choosing `deployment`; this revalidates/reloads the mount before auditing and swapping. It does **not** overwrite archived snapshots or mount points. An audit/validation error never modifies the live resolver. The operation does not pause uploads, downloads, sync or running analyses.

**Not yet delivered:** durable global desired dataset binding, multi-replica distribution/acknowledgment, restart persistence, upload/staging over HTTP, secure host-level filesystem replacement and fleet rollback. Those require separate preparation, deployment ownership and verification; saved snapshot metadata alone cannot claim any of them.

**Acceptance:** tests for malformed fingerprint, role restrictions, stale revision/active version, corruption, audit unavailable, successful local apply and explicit deployment restore, same-instance radius reconcile preserving archived content, and Go Client/Agent/Web/Desktop parity, plus authoritative full exact-head PR CI before merge.


### P1-B3c: persistent desired GeoNames dataset and restart verification

This phase builds on the temporary P1-B3b control above. The administrator can now choose a versioned archived dataset or return to the operator's deployment mount as the **persisted desired** content source. The GeoNames settings table stores one optional SHA-256 content address together with the matching radius under the existing revision and transactional audit. Existing deployments migrate to the empty-fingerprint default. The dataset selection changes the revision; historical rollback still changes **radius only**, preserving the selected data source.

- A dataset apply request first checks the current effective fingerprint/version and desired configuration revision, reconstructs the complete immutable resolver from SHA-256-verified local snapshot bytes (or the trusted deployment mount), then commits target fingerprint + incremented revision + immutable radius history + metadata-only audit in a single PostgreSQL transaction. Only after commit does the responding Server hot-swap the immutable pointer. Failed validation, stale writes or audit failures leave desired and active values unchanged.
- At bootstrap, the Server reads the desired radius, fingerprint and revision in one query. It verifies an archived selection using the existing manifest, file size/symlink bounds, full hash and indexed resolver build, and acknowledges the revision only on success. If the local archive is absent or corrupted, it may serve the deployment-backed resolver as a fallback but **must not claim the desired archive is applied**. If even the optional default cannot load, file uploads, downloads and synchronization continue with GeoNames unavailable.
- Every replica's 30-second reconciliation compares both desired radius and dataset fingerprint. It independently verifies its **local** bytes, then rechecks the same desired revision before swapping. A failed/missing archive leaves last-good runtime in place; heartbeat acknowledgements include effective fingerprint and revision, without exposing host paths or replica identities. Aggregation covers only observed-live instances; it cannot prove full-fleet convergence.
- Admin GET returns both desired_dataset_fingerprint and active_dataset_fingerprint plus effective revision, apply_state and active_dataset_persistent. The latter reports **current-instance observed matching of the stored desired state**, not guaranteed future availability. Shared Web/Desktop present the desired-versus-effective source and disable the persistent-selection claim against older Servers/Agents.
- No file upload, arbitrary host paths, automatic cross-node distribution, Docker socket or process restart. Per-user Yike, Synology and Sync Folder data remain excluded. Real fleet artifact distribution, target retention and distributed rollback are separate P1-B3d+ phases.

Acceptance requires Go/PostgreSQL corrupted archive and restart selection cases, version conflict and audit rollback, pinned in-flight snapshot preservation, replica fingerprint proof, Web/Desktop contract parity and exact-head green GitHub CI. Runtime testing on a production persistent mount is a distinct unverified gate.


### P1-B3d1: administrator-recovery of a missing desired GeoNames archive on one Server

This phase provides a narrow real repair rather than an unsafe general filesystem or container controller. An administrator whose saved desired GeoNames archive directory is **absent** from the currently responding Server can try to reconstruct it from that Server's existing trusted, read-only `XD_PHOTO_PLACE_GEONAMES_DIR` mount. A missing archive directory is not evidence that the mount still contains the original bytes, so the page never promises success before the actual operation.

- Admin-only `POST /api/v1/admin/services/geonames/dataset-snapshots/restore-missing` accepts only `revision`, `expected_version` and `expected_fingerprint` from current status. **No client-selected target**, path, files or remote addresses. The target is always the persisted desired SHA-256 fingerprint; the endpoint requires a loaded current resolver and an operator-provisioned separate private archive directory.
- Acquire the existing per-process snapshot and reload locks, verify the expected current runtime and desired revision, and require the recorded immutable manifest. Recopy **only** `cities500.txt`, `admin1CodesASCII.txt` and `countryInfo.txt` to a private staging directory, with regular-file/symlink/size limits, full content SHA-256 matching the desired fingerprint, byte count matching the manifest, and complete immutable resolver validation at the current desired radius. A source mismatch returns 422 without modifying active or stored data.
- Never overwrite or remove an **existing** archive destination, even if corrupt or a symlink. A corrupt-but-present archive requires a separate restricted operator intervention (or an administrator's explicit switch to the trusted deployment source through the established versioned apply control), not a self-service delete/move. This stage does **not** distribute datasets or repair arbitrary host paths.
- Under the persisted GeoNames row lock, reject stale revision/fingerprint/radius, publish the previously validated private directory only if the exact target is still missing, and persist a metadata-only admin restore audit in the same guarded operation. If audit/commit fails, remove the **newly created** destination and leave desired settings and in-memory last-good resolver untouched; the filesystem and database are not advertised as a fleet transaction. Only on successful audit does this process swap its immutable resolver and acknowledge the **unchanged global desired revision**. Pinned PlaceRunner batches remain consistent; no durable transfers are cancelled.
- Admin GET reports `missing_archive_state` as `not-selected`, `missing`, `present-unverified`, `invalid` or `unavailable`, plus `restore_missing_enabled` and a prerequisite. It performs a cheap directory existence check, **never a fresh hash**; successful runtime apply is separately confirmed by the existing desired/effective revision and fingerprint. Web/Desktop share the same explicit confirmation and read-only status. Old Agents or Servers without the optional capability cannot show a functioning restore button.
- Only the responding Server is modified. Multi-replica cryptographically verified transfer, repairing existing corrupt directories under crash-safe maintenance, and a complete cluster deployment/rollback controller remain outstanding P1-B3d2+ phases. Per-user 同步文件夹, Yike, Synology and DSM settings are excluded.

**Acceptance:** PostgreSQL integration tests for admin/member/anonymous, malformed and stale current version, wrong trusted source bytes, existing corrupted directory untouched, failed audit rolling back a newly staged directory, successful exact restore with in-flight snapshot pinning, unchanged desired revision and verified next startup; Go Client HTTP and Web/Desktop IPC/UI wiring tests, full exact-head PR CI. A real mounted production volume and multi-server rollout are still separately untested.


### P1-PG1: versioned, hot-applied xDrive Server PostgreSQL connection pool

The global administrator **服务与依赖** page now manages a real, narrowly bounded piece of PostgreSQL integration: each xDrive Server process's Go `database/sql` pool. This is **not** a PostgreSQL daemon, container, schema, data volume or credential editor.

- `GET/PUT /api/v1/admin/services/postgresql/pool`, `GET .../revisions`, and `POST .../rollback` are behind the existing Server `requireAdmin` authorization. `xd_admin_postgres_pool_settings` stores the desired `max_open_connections` and `max_idle_connections` with an optimistic revision. `xd_admin_postgres_pool_revisions` is an immutable audit-friendly journal, including revision zero on first edit. A saving/rollback transaction contains the desired setting update, history and metadata-only administrator audit; an invalid request, stale revision, missing audit table or invalid saved history prevents change.
- Bounds are **max open = 0 (keep Go's original unlimited default) or 8–256**; **max idle = 0–32**, never greater than nonzero max open. The minimum managed nonzero open limit avoids extreme one-connection bottlenecks. Both integer values are required; omitted fields never become implicit zero limits. No database URL, password, Docker socket, restart command, host path, environment editing, per-user source credential or database parameter change is accepted.
- Only once the database transaction commits does the responding Server invoke `sql.DB.SetMaxOpenConns` and `sql.DB.SetMaxIdleConns` on its shared Gorm `sql.DB` handle. The observed `sql.DB.Stats().MaxOpenConnections` and a locally held effective revision/values must match before `apply_state=applied`. The ordinary PostgreSQL ping-based readiness probe remains independent from connection-pool configuration. `unmanaged` means no saved admin revision (Go's default values are informative only); `pending` never silently becomes green.
- Each Server independently reads saved settings and applies them at startup before its background tasks begin, then attempts best-effort 30-second reconciliation on later revisions. Other replicas do not share a process pool or instant activation, and this phase has no comprehensive cluster inventory; the UI must label **current Server only**, not all replicas. Failures preserve the previous local pool until a valid desired setting is committed/applied.
- The shared Web/Desktop MUI panel includes actual pool open/in-use/idle stats, bounded editable values, save confirmation, desired/effective revision and parameter comparison, safe revision history/rollback, and explicit in-app versus deployment-only boundaries. The Desktop path is Electron -> Agent IPC -> authenticated Go Client -> admin Server and has the same input validation. Admin-only contract tests guard Web/Desktop parity.
- No container lifecycle, JDBC/server-side `max_connections`, SSL/TLS credentials, backend memory/CPU limits, PostgreSQL version upgrade, schema migration, data migration, or storage relocation is managed here. Those require a separately permissioned Host Manager/maintenance flow and genuine health/readiness validation. Changing the Go pool may influence queue latency and should be evaluated against workload/number of Server replicas; it must not cancel durable transfers or restart the application.

**Acceptance:** Go unit and PostgreSQL integration proving default/unmanaged, strict bounds, role restrictions, optimistic revision fencing, real `sql.DB` max-open mutation, independent replica reconciliation and restart restoration, append-only revision/audit history, failure on missing audit, actual rollback; Go Client/Agent/Electron/Web shared contracts, Go/Windows/Web/Desktop PR CI and final gate. Production workload and multi-host deployment measurement remain separate.


### P1-PG2: observed-live PostgreSQL pool reconciliation and status (implementation)

Builds on P1-PG1 without changing the privileged configuration contract. Read-only current/fleet-**observed** verification is added; the PostgreSQL daemon, Docker, per-user 同步文件夹 and durable transfers are unaffected.

- Every Server publishes one ephemeral row in `xd_postgres_pool_replica_presence` every five seconds, expiring after 20 seconds. The private ID is a process-only random key. Effective revision and MaxIdle come from its installed local policy; MaxOpen is checked against `sql.DB.Stats().MaxOpenConnections`. Inconsistent/unmanaged runtime states never acknowledge a revision.
- The existing administrator-only, no-store `GET /api/v1/admin/services/postgresql/pool` response adds a `replicas` aggregate containing state, bounded observed/applied/pending/unmanaged counts, policy revision/limit groups and truncation. This is optional for older Server/Agent consumers. No individual instance ID, hostname, path, credential, DSN or raw error escapes the Server.
- Reads ignore expired, stale or far-future heartbeats and are capped at 100+1 rows; unknown schema/database failures return `unknown` without disabling the local editor. `applied` requires a nonzero desired revision, nonempty observed set and exact matching revision and both limits from every fresh observed row, without truncation. No heartbeats are `unavailable`; default unmanaged policy is `unmanaged`. Aggregation does not prove the set of *all deployed* replicas.
- The canonical shared MUI panel in Web/Desktop displays the observed-only counts, grouped policies and state independently from this Server's actual pool stats. - Postgres server-side connection caps, DSNs/credentials, persistent volumes, replicas missing from heartbeats, capacity planning and Host Manager lifecycle operations are still outside this phase. ### P1-M1a: real isolated FFmpeg/FFprobe runtime readiness

**Scope:** the 11-row Web/Desktop shared administrator page now distinguishes **disabled** (no media worker socket configured), **unavailable** (configured, failed/invalid live probe) and **ready solely for FFmpeg/FFprobe executable health**. A successful probe does NOT mean the media task protocol, queue, transcoding, previews or cancellation are implemented.

The same binary can run as an independent service with `xdrive-server media-worker serve` (and be inspected with `xdrive-server media-worker check`). This command never loads DB credentials, JWT keys or the file store. It requires a trusted operator-installed FFmpeg and FFprobe on the *worker* host. Every `GET /v1/info` over the private Unix Socket verifies both actual subprocesses by running only fixed `-version` arguments under bounded time and output, then returns a strict protocol version and `task_execution_supported=false`. Arbitrary file paths, user-supplied URLs, shell commands and media tasks are not accepted. The socket is mode 0600; it cannot replace an existing file, symlink or active listener. Only validated version strings and safe static status messages reach administrators, never raw errors or the socket location.

**Manual operator opt-in:** the installer provisions `XD_MEDIA_WORKER_RUNTIME_DIR` (by default the private host `~/.xd/state/media-worker` directory). Run the independently installed worker binary under the SAME numeric UID as xDrive Server, with FFmpeg/FFprobe installed and `XD_MEDIA_WORKER_SOCKET=<HOST_RUNTIME_DIR>/media-worker.sock`. The Server mounts that directory read-only as `/run/xdrive-media-worker`. For the Server set `XD_MEDIA_WORKER_SOCKET=/run/xdrive-media-worker/media-worker.sock`; leave this empty to keep the optional dependency disabled. Ensure the runtime owner and filesystem permissions allow the mode-0600 socket to be read by Server. A failed optional worker never prevents core startup, upload/download or sync.

The default xDrive Server image is distroless and has no FFmpeg binary. This stage does NOT publish an installable separate media-worker image, container controls, media job API, configured concurrency, audited dynamic policy, resource-tuning UI or real transcode throughput measurements. These are separate P1-M1b+ phases and cannot be represented by a green task status.

**Validation:** Go Unix server/client protocol and fixed-command tests, refusal to overwrite untrusted entries, shutdown cleanup, malformed and oversized response rejection, admin safe status/permission checks, Desktop source parity and authoritative complete PR CI. Actual host deployment and codecs remain unmeasured.
