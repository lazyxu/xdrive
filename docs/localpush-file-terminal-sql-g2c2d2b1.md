## Schema and lock discipline

`meta.LocalPushFileTerminal` is a Server-private, all-`json:"-"` single-decision slot with unique `operation_id` PK, unique `stage_id`, and unique (`source_id`, `generation`). Every row carries current original Owner+session, Device, strong Root/fingerprint, Source revision/target, request-key digest, immutable Stage path/snapshot/content identity, size, native witness *correlation digest*, state, physical SQL Node/SourceItem IDs (positive only), and database record time. The only two reserved terminal state strings are `physical-commit` and `physical-cancel-quiesced`. An arbitrary string/digest or reservation expiration never proves either outcome.

The SQL-only `inspectBoundLocalPushFileTerminalTx` requires a caller-held real GORM PostgreSQL transaction, live original account/device/Root authorization, exact original 32-byte private key, operation UUID+generation, immutable Stage binding, and canonical original SQL COMMIT for positive state. For negative state it requires absence of original SQL COMMIT. Unknown state, missing table, altered scope/Stage/content, wrong original key, missing canonical commit or crossed COMMIT/CANCEL history all fail closed. **The read returns only an internal SQL correlation record.** It does not independently verify current physical CAS or a native held file. B2/B3 must provide that evidence before a terminal recorder or a trusted public result exists.

`requireLocalPushFileTerminalVacantTx` is applied **inside the held owning operation transaction** to current physical first-file writer admission, reservation replay/new generation, reservation abort, and reservation terminal observation. A terminal row from ANY Source generation (or unavailable schema) vetoes those transitions. The required order is Owner SHARE -> Device UPDATE -> Source UPDATE -> Root SHARE -> original/current Operation UPDATE/SHARE -> immutable binding/terminal SHARE -> CAS/Node. Future terminal writers MUST first acquire the same original Operation UPDATE lock; uniqueness indexes alone do not prevent a racing writer. No records are generated by migration, initialization or this PR, and no routine converts timeout/lease expiration to physical CANCEL.
