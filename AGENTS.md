# AGENTS.md

## Continuation progress reporting

For every follow-up request to "continue" an ongoing development, audit, or CI/PR cleanup initiative, **begin the user-visible response with a concise state report before changing code or PRs**:

1. State the exact repository/provider, fixed master or work-branch baseline, and **current phase** (for example L01-A).
2. List **completed work** with concrete commit/PR/CI/merge evidence; distinguish implementation, test execution, green CI, and merged delivery. Never label planned or merely reviewed code as complete.
3. List **remaining gaps**, blockers, and the next bounded, testable step. Preserve named constraints from previous turns.
4. Inspect only materially related existing branches and PRs first. Prefer a viable unfinished branch; close superseded/abandoned related PRs and delete merged or proven-obsolete related branches only after checking their diffs and merge state. Do not clean unrelated work.
5. End each implementation turn with the updated phase, evidence-based done/not-done summary, test/CI status, and branch/PR disposition. Repeat this handoff at the beginning of the next continuation.

The progress report is required even when no code changes are possible. Follow the provider-specific GitHub/GitLab delivery and single-work-commit rules below; do not claim a GitLab push or cleanup if it was not actually performed.

## Repository workflow

For every code change in this repository, use this workflow by default:

Provider delivery rules:

- **GitLab:** after the applicable local validation passes, make a normal commit on the latest GitLab `master` and push it directly to `gitlab/master`. Never force-push. Treat the resulting GitLab `master` pipeline as the authoritative post-push validation; if it fails, diagnose it and fix forward with another normally pushed commit.
- **GitHub:** never push changes directly to `origin/master`. Push an exactly-one-commit short-lived branch, open a PR targeting `master`, require the PR CI to pass, and merge it with linear history.
- **Changes for both providers:** start from a commit shared by both masters whenever possible, validate locally, push the commit directly to GitLab `master`, and push that same commit to a short-lived GitHub branch for a PR. Do not push it directly to GitHub `master`.

1. Run `git fetch origin` and `git fetch gitlab` first when both remotes exist.
2. Before creating or continuing a work branch, reconcile only branches that are materially related to the current task, dependency chain, or touched subsystem:
   - inspect related unmerged branches for their diff, PR/MR state, CI state, conflicts, and unfinished work;
   - continue a viable related branch instead of duplicating the same work;
   - delete related branches whose commits are already fully contained in `origin/master`, or that are abandoned, duplicate, or superseded;
   - keep a related branch only when there is a concrete reason it cannot yet be merged or deleted, and state that reason.
   Do **not** inspect, wait on, merge, rebase, or otherwise manage unrelated branches/PRs/MRs merely because they exist. Unrelated work may proceed independently unless it creates an actual merge conflict or changes a dependency required by the current task.
   Do not start a fresh implementation while an older viable half-finished branch for the same or directly related work is still unresolved.
3. After reconciling the current task's related branches, fix the work baseline immediately and do not let unrelated later `master` movement churn the branch. GitLab work may continue on a clean local `master` based on `gitlab/master`; GitHub work uses a new short-lived branch from the selected `origin/master` baseline when no related existing branch should be continued. Create or preserve the branch's single work commit immediately after selecting that baseline.
   - Every short-lived work branch must carry **exactly one work commit above its selected base at all times after the first commit is created**. Do not accumulate follow-up, fixup, or "temporary" commits with the intention of squashing them later.
   - After the first commit, fold every subsequent change into that same work commit with `git commit --amend` (and force-push only the non-`master` work branch when needed). Keep the branch single-commit throughout development, review fixes, and pre-merge reconciliation.
   - For closely related dependent phases, do **not** wait for an upstream PR/MR to merge before continuing. Pull/reuse the active work branch directly, or create a short-lived stacked branch from its current tested head when that is the fastest safe path.
   - A stacked/dependent branch must likewise add exactly one work commit above its immediate dependency branch. After the dependency lands, rebase/reconstruct that one commit onto the latest `origin/master`; never use a late squash as normal cleanup.
   - Do not block implementation merely because a related PR is waiting on CI/review when the dependency branch is available and its current tree is suitable for continued work.
4. Make the requested change only on the selected delivery branch, or on the clean local `master` selected for a GitLab direct push. Preserve the one-work-commit invariant on every short-lived GitHub branch.
5. Add or update relevant tests.
6. Run the applicable local tests and require them to pass before opening or updating the PR/MR.
7. Before the first delivery push, fetch the target remote again to detect real integration problems, but do not chase unrelated `master` movement after the work baseline has been fixed. For GitHub, keep the existing single work commit on its selected baseline when the PR remains mergeable; reconstruct that one commit onto the newer `origin/master` only when GitHub reports the PR cannot be merged because of an actual conflict, or when repository rules explicitly require an update. For GitLab, update the clean local `master` from `gitlab/master` before committing or pushing. Do not rebase merely because `master` has unrelated newer commits or merely to retrigger CI.
8. Before the first full GitHub PR validation, verify that the work branch is already exactly one commit relative to its merge base; do **not** plan a final squash after CI. For a normal branch based on `origin/master`, verify with:

   ```bash
   git rev-list --count origin/master..HEAD
   ```

   The result must be `1`. A result greater than `1` is a workflow violation to fix before full PR/MR validation, not an expected pre-merge cleanup step. The purpose of keeping the branch single-commit from the start is to avoid a late squash/force-push that causes an otherwise unnecessary additional CI run.
9. For GitHub, push the branch and open or update the PR; its CI is the authoritative pre-merge validation. For GitLab, push the locally validated commit directly to `gitlab/master`; its `master` pipeline is the authoritative post-push validation. Once the applicable pipeline is green, do not push, rebase, amend, squash, or otherwise retrigger CI unless the source tree must change.
10. If `origin/master` advances after CI is green, ignore unrelated commits and merge the already-tested PR directly when it remains mergeable. Reconstruct/rebase only when repository rules require it or an actual merge conflict makes the PR unmergeable. Any required reconstruction changes the tested commit and therefore requires the PR/MR CI to run again.
11. Merge an already-single-commit GitHub PR into `master` using a linear-history merge. GitLab changes are already on `master` through the validated normal push. Do not rely on squash merge to repair a multi-commit work branch.
   - For GitHub, the successful PR CI run is the merge gate. **After the PR merge succeeds, do not wait for, poll, or block subsequent work on the `master` push CI triggered by that merge.** Proceed immediately to cleanup and the next task.
   - Treat GitHub `master` CI as an asynchronous post-merge defense, not a second completion gate for the already-merged PR. If that later pipeline reports a regression attributable to the merged change, diagnose it and fix forward in a new normal PR; unrelated follow-on work must not wait for that pipeline to finish.
12. After the merge succeeds, delete the merged remote branch through the repository cleanup automation:
   - GitHub: `.github/workflows/cleanup-merged-branches.yml` runs on pushes to `master` and safely removes redundant merged branches, including rebase-merged PR branches whose original head SHA no longer appears in `master` history.
   - If an automatic cleanup run is missed or delayed, use that workflow's `workflow_dispatch` entry point instead of requiring a locally authenticated branch-delete command.
   - Verify the merged branch is gone after cleanup; do not leave superseded task branches around.
13. Keep long-lived branches to a minimum.



## Race and concurrency specialization policy

- For a race/concurrency specialization task, **test first and do not change production behavior until a real failure is reproduced**. Continue running or extending the relevant race/stress/interleaving tests until one of them fails because of an actual product concurrency/lifecycle bug.
- A test harness, fixture, mock, parser, selector, timing assumption, CI infrastructure issue, or unrelated existing failure does **not** count as the required reproduction. Fix the test/harness itself and rerun without changing production code.
- The first-red evidence must be deterministic enough to identify the violated contract (for example: stale completion overwrites a newer scope, old lifecycle retains busy ownership, duplicate same-tick submission, old request crosses account/session identity, or a newer revision is regressed). Record that failing assertion/path in the PR description or test name.
- If no real race failure can be reproduced, keep testing/auditing; do not land speculative synchronization, generation fences, locks, cancellation, or lifecycle resets merely because a race appears theoretically possible.
- Only after a real first-red is confirmed may production code be changed. Make the smallest fix that addresses the reproduced ordering/lifecycle failure, and preserve existing platform semantics unless the failing contract proves they are wrong.
- After the fix, require the **same reproducer** to turn green, then run the materially related race/concurrency suite and normal subsystem tests. A replacement test that avoids the original failing interleaving is not sufficient.
- Race/concurrency branches follow the normal related-work rule: inspect and continue viable related branches/PRs first, avoid duplicate fixes, and keep the GitHub branch at exactly one work commit. Test-first revisions and production fixes must be amended into that same work commit rather than accumulated as fixup commits.
- Merge only after the reproduced race is fixed, the relevant regression suite is green, and the repository's normal authoritative CI gate passes. Do not merge a branch that is only statically plausible, partially tested, or still failing the original race.
- This policy applies equally to FileExplorer, Gallery/Photo UI, transfers, thumbnails, background tasks, sync, navigation/session lifecycle, caches, and any other subsystem where the task is specifically a race/concurrency investigation.

## Performance specialization policy

- Before starting or continuing a performance task, inspect only the materially related open branches/PRs/MRs and the canonical performance document for that subsystem. Continue a viable related branch before opening a duplicate implementation. Already-merged, superseded, or abandoned performance branches must not be treated as active work.
- Every performance track must have a canonical document under `docs/` (for FileExplorer, use `docs/file-explorer-performance.md`). The document is part of the performance contract, not optional release notes.
- Every performance PR/MR must update its canonical performance document in the **same change** with the current status and evidence for that specific work item. Record at minimum: status, workload/data shape, scale, benchmark or trace command/tool, sample count when applicable, BEFORE baseline, AFTER/current result, units, delta, acceptance/rejection decision, regression budget when one exists, and the next action.
- Performance optimization is measurement-gated: **measure the current implementation first on the stable named workload before changing production code**. If the current result is already within the documented budget/acceptance target, keep the implementation unchanged and record that decision. If it is not, state the acceptance threshold before experimenting, make the smallest performance change, then rerun the **same workload, environment, units, and sampling method**. Keep the production change only when the improvement is material and repeatable beyond normal benchmark noise and no important CPU/RSS/I/O/request-count/correctness dimension regresses; otherwise revert the production change and record the experiment as **Rejected / no material gain** with its BEFORE/AFTER evidence.
- Use explicit status labels such as **Planned**, **Benchmarking**, **Measured baseline**, **In progress**, **Accepted**, **Rejected**, and **Merged**. Do not leave a completed optimization documented as merely planned, and do not leave an active benchmark without a status.
- If a change has no comparable wall-clock BEFORE/AFTER measurement, mark it clearly as **unmeasured / complexity-only** and do not quote a timing or percentage speedup. Structural improvements such as bounded concurrency, fewer allocations, fewer SQL round-trips, or bounded retained metadata may be documented with those exact structural metrics.
- Benchmark-only PRs/MRs must write their measured output back into the canonical document before merge. CI logs are transient evidence, not the durable performance record. If the benchmark result is produced by CI, amend the documentation with that exact result and rerun the authoritative validation because the source tree changed.
- Keep accepted and rejected experiments in the performance document. A rejected index, cache, batching policy, or concurrency change should retain its measured data and rejection reason so the same low-value experiment is not repeated later.
- Large-scale scenarios must use stable, named workloads. When a subsystem claims 10k/100k scalability, document the exact logical item count, viewport/range behavior, thumbnail/cache state where relevant, and whether the run measures pure controller CPU, browser/Electron rendering, network/IPC transport, decode/generation, or end-to-end latency.
- Performance CI jobs should be scoped to the branch/workload that needs them unless they are stable enough to become a permanent regression gate. Do not turn a noisy exploratory benchmark into a required global CI gate before its variance and budget are understood.
- **Viewport/request-scoped cancellation performance:** when a virtual range, thumbnail or preview is no longer consumed after scrolling, navigation, view/window teardown, or lifecycle changes, propagate cancellation through the owning Web `AbortSignal` or Desktop Renderer → Main → Agent IPC down to the HTTP request context and Go handler; measure actual upstream abort, active request count and payload waste, not only stale-result suppression. Scoped cancellation must not terminate durable Task Center uploads, downloads, synchronization, deletion, or shared background maintenance merely because a window changes. Reused/background tasks need their own lifecycle and consumer-aware semantics.

## Cloud storage inventory policy

- **`docs/storage-inventory.md` is normative** for Server physical-storage accounting, cache classification, host-path display, and storage cleanup. Read and follow it before adding or changing any Server-side persistent cache, derivative, temporary directory, database/storage sidecar, backup class, or other xDrive-managed file class.
- Every administrator storage-inventory row must expose the resolved **host absolute path**. Never show environment templates such as `$XD_FILES_DATA_DIR/...`, unresolved relative paths, or container-only mount paths such as `/data/...` as though they were host locations.
- Any new persisted Server file class must define its inventory category, resolved host path, byte-accounting relationship, canonical/regenerable/temporary/read-only status, and safe cleanup semantics in the same change. Unknown/unclassified xDrive-reserved data is counted but is never automatically deleted.
- Cache cleanup may remove only explicitly regenerable or lifecycle-safe temporary data. It must never delete CAS/legacy canonical content, PostgreSQL data, backups, trash/history canonical content, Source identities/bindings/credentials, PhotoAsset/PhotoResource/PhotoMetadata canonical data, host configuration/program/log/state data, or unclassified files.
- Do not broaden API-container host access merely for storage accounting. Host-only directories are measured by the existing host-control boundary and exposed to the Server as aggregate counts/sizes plus already-resolved display paths; do not mount secret-bearing host directories into the API container.
- Web and Desktop must use the shared `XDriveCloudStoragePage` and shared storage models. Keep REST, Electron, and Agent IPC as thin platform adapters instead of forking storage presentation or cleanup semantics.
- Physical totals must be non-overlapping at their declared aggregation level. In particular, backup subcategories are detail rows under the backup root, and file-data cache/staging categories are detail rows under the file-data root; do not double-count child categories in `total_managed_bytes`.

## Asynchronous task and cancellation policy

- Keep cancellation work **scoped to the feature or subsystem currently being changed**. Do not start a repository-wide cancellation retrofit merely because another asynchronous subsystem is missing a control. Existing async cancellation gaps are handled when that subsystem is materially touched, explicitly requested, or becomes necessary for correctness.
- New or materially reworked long-running, user-visible asynchronous work should design safe cancellation as part of that work when cancellation is meaningful. Web and Desktop must use the same business semantics through platform adapters; do not intentionally ship one client with cancellation and the other without it for the same cross-client operation.
- **FileExplorer Folder Properties is the canonical request-scoped example.** Recursive folder statistics must run on Server data, never by walking the directory tree in Web/Desktop. The request is automatically cancelled when the Properties dialog closes, its target selection is replaced, or the owning surface unmounts. This operation does **not** create a durable Task Center entry and does not require a separate visible Cancel button.
- Web request-scoped cancellation uses `AbortController` / `AbortSignal`. Desktop must propagate the same cancellation through renderer -> Electron/Agent IPC -> Server request context rather than merely ignoring a late renderer result. Server handlers and database work must use the request context so cancellation can interrupt the recursive query.
- Cancelled request-scoped work is a normal lifecycle outcome: do not show a failure toast for an intentional abort, and never apply a stale result after a newer Properties request has started.
- Durable/background tasks that already participate in Task Center continue to use the existing shared task/control contract and Server-returned `control_actions`. Do not remove or fork existing cancellation semantics while working on an unrelated feature.
- When a task later touches an existing subsystem such as transfers, thumbnails, analysis previews, media indexing, Photo Intelligence, synchronization-folder runs, archive preparation, or maintenance, evaluate cancellation **inside that task's scope**. Add or improve cancellation when it is safe and useful, but do not proactively sweep those subsystems from an unrelated PR.
- Shared/singleflight work needs consumer-aware semantics **when that subsystem is being modified**: cancelling one waiter must detach that waiter, and must not incorrectly terminate work still needed by another waiter or a background owner.
- Cancellation must preserve storage and metadata integrity. Do not interrupt an indivisible commit that cannot be made safe. Temporary files, reservations, partial derived artifacts, and in-memory state must be cleaned up or left in a deterministic resumable/retryable state at safe boundaries.
- Tests for request-scoped cancellation must cover automatic abort on owner-surface close/replacement, stale-result suppression, no user-visible error on intentional abort, and actual propagation to the Server request context. Tests for durable task cancellation should follow that subsystem's existing lifecycle/control contract when it is touched.
- **FileExplorer non-performance design is normative.** Before changing FileExplorer behavior, selection, navigation, properties, drag/drop, shell integration, or other non-performance interaction contracts, read and follow `docs/file-explorer.md`. Performance-only work remains governed separately by `docs/file-explorer-performance.md`.

## Synchronization folder management policy

- The user-facing name for the connector-backed `Source` subsystem is **同步文件夹**. Web/Desktop navigation, dialogs, empty states, help text, and actions must use “同步文件夹” rather than “外部来源” or generic “来源” when they refer to this subsystem. Internal Go/TypeScript model names, API routes, and database tables may continue to use `Source` / `ExternalSource` / `xd_sources`; do not perform a storage/API rename merely for UI terminology.
- Every synchronization folder settings surface must show the persisted xDrive target as a **read-only target directory**. The server is the source of truth and should expose a resolved `target_path` derived from the stored target node. Clients must not reconstruct a managed path from display templates once a target exists.
- Ordinary settings saves must not silently move, rename, recreate, or rewrite the target directory. A target changes only through an explicit target-selection flow or a connector-owned identity/binding operation. Managed connectors such as Yike may validate or repair their deterministic hierarchy while binding a verified account, but changing schedule, run mode, status, ignore rules, or credentials for the same identity must not casually relocate data.
- Server-stored connector credentials remain encrypted at rest. Normal list/status/test APIs return only credential metadata and never plaintext. When a product requirement allows the signed-in owner to inspect a stored secret, expose a separate explicit **reveal** action that is owner-scoped, audited, `Cache-Control: no-store`, and returns only a connector-specific allowlisted secret field (for example Yike `cookie` or Synology Pull `password`) rather than the whole credential payload.
- Web/Desktop must never reveal a stored credential automatically. Show a mask by default, fetch plaintext only after an explicit user click, keep it only in renderer memory, automatically hide/clear it after about 30 seconds, and clear it when the settings surface closes. Never write revealed values to logs, diagnostics, local storage, clipboard automatically, or an editable replacement field.
- “Show stored credential” and “replace credential” are separate UI operations. Revealing the old secret must not populate or submit the replacement input. Leaving the replacement input empty preserves the current stored credential.
- New synchronization-folder connectors should adopt this target/credential behavior by default. If a connector does not store credentials on xDrive Server (for example a NAS-side Push agent with local credentials), omit server-side reveal rather than copying the secret into xDrive merely to satisfy UI symmetry.
- Web and Desktop should reuse the same shared MUI target/credential presentation primitives; connector/API state and mutation logic remain client-local.
- **Source/media design documents are normative.** Before changing a synchronization-folder connector, Source models, Source scheduling/reconciliation, or media projection triggered by Source imports, read and follow `docs/external-source-architecture.md` and `docs/photo-source-v2-roadmap.md`. If implementation and those documents disagree, reconcile the design explicitly in the same change rather than silently creating a second contract.
- **Preview Engine design is normative.** Before changing ordinary file preview, preview transport, FileExplorer Inspector preview, Gallery ordinary Image/Video presentation, or non-destructive media-edit transforms, read and follow `docs/preview-engine.md`. PDF/Video/Audio/Image must share the classifier, signed preview source, and `FilePreviewSurface`; non-destructive Gallery edits must remain versioned source-bound recipes rendered through that shared engine rather than app-local renderers or rewritten originals. Do not add media-specific playback APIs or a second binary preview stream. Keep Live Photo/EXIF/GPS/Favorite/Tags/People/Albums in the Gallery media-semantic layer.
- **Photo Intelligence design is normative.** Before changing automatic face detection/embeddings, person clustering, reverse-geocoded place names, visual/OCR intelligence, semantic embeddings/search, or their Gallery facets, read and follow `docs/photo-intelligence.md`. Photo Intelligence operates only on local `PhotoAsset` / `PhotoResource` / `PhotoMetadata` state; it must not import provider semantic metadata, mutate Source state, or overwrite user-managed Favorite/Tags/People/Description/albums.
- Durable Photo Intelligence person identity is **user intent**, not analyzer state. Persist long-lived people through `PhotoPerson / PhotoPersonAsset` and stable `person:v1:<uuid>` ids. Never use `PhotoFace.ID`, automatic cluster ids/keys, embedding similarity, or provider person ids as the durable user identity; never implicitly mirror durable-person mutations into legacy/manual `PhotoMetadata.PeopleJSON`.
- Synchronization-folder connectors are a **file synchronization layer only**. They may use provider APIs for authentication, file enumeration/identity/path/size/revision/digest hints, original-byte download, and proven change/tombstone contracts. Do not add provider-specific dependencies for canonical EXIF, GPS/geolocation, image/video technical parameters, thumbnails, Live Photo pairing, RAW/sidecar/burst grouping, people/tags/favorites/descriptions, or other media semantics.
- Canonical media metadata and relationships must be derived by xDrive from the preserved original files after `Node + File + CAS` commit. The same original must produce the same media result regardless of whether it came from Yike, Synology Photos, FileStation, Push, upload, Web, Desktop, FUSE, or CfAPI.
- Live Photo projection must be local and evidence-based: validated `.livp` structure, matching embedded Apple asset/content identifiers, or another deterministic local container/embedded identifier. Never make provider `live_type`, provider pair IDs, filename similarity, or timestamp proximity the canonical pairing source.
- Provider collection APIs may be retained only for file discovery or optional source provenance; collection/semantic API failure must never gate ordinary file backup, media indexing, or deletion inference.

## CI policy

- **Test-container images are runtime/toolchain images, not snapshots of the current business source tree.** For ordinary unit/integration/E2E/benchmark jobs that execute current repository code inside Docker, follow the normative contract in `docs/ci-test-images.md`: bake only stable OS/runtime/toolchain/system-library/third-party-model dependencies into the reusable test image, then bind-mount the checked-out business source, tests, scripts, and generated artifacts needed by that run. Source/test mounts should be read-only by default; writable mounts are limited to declared build/output/cache/runtime directories.
- Do **not** add a new test-image Docker stage that `COPY`s changing xDrive business source/tests and runs them during `docker build`. A normal source/test-only change must not require rebuilding a materially different test image. Rebuild the reusable test image only when its runtime dependency contract changes (base image, OS packages, language/runtime dependencies, native libraries, model/runtime assets, or equivalent image inputs).
- The exception is **exact-artifact/release-image validation**: when CI is explicitly proving the final server/Caddy/photo-face/client artifact that will be published, test the exact produced image/artifact byte-for-byte and do not mask or replace its packaged business code with a bind mount. When both fast source-mounted testing and final-image validation are needed, keep them as separate stages with separate purposes.
- Existing test-image paths that still bake mutable business code are migration debt. Convert them to the mounted-code contract when that test image is materially touched; all newly added test-container paths must comply immediately. GitHub/GitLab equivalents must preserve the same contract.

- Full CI runs for GitHub pull requests or GitLab merge requests targeting `master`, and also for direct pushes to `master` on both providers. Ordinary pushes to short-lived feature/fix branches do not run full CI.
- GitHub `workflow_dispatch` and a GitLab Web/Run pipeline are the equivalent manual full-CI entry points.
- A successful GitHub PR CI run is the authoritative pre-merge test gate. After a GitHub PR merges, do not wait for or monitor the resulting `master` push CI before continuing with the next task; that pipeline runs asynchronously as a post-merge safety net. GitLab uses local validation before its direct `master` push and the resulting `master` pipeline as the authoritative post-push gate. Keep GitHub branches single-commit before PR CI so no late squash is needed solely for history cleanup.
- Client packaging follows **Build Once / Publish Exact Artifact**, with **Test Exact Artifact** as the stable-release gate. `desktop-linux`, `desktop-windows`, and `build-client-core` build the reusable client components; `package-linux-client` and `package-windows-client` assemble the only user-facing installers independently of ordinary source/server/web tests, so installer production continues even if an unrelated test fails. Exact-artifact tests wait for and consume only their corresponding installer artifacts. Publishing must consume those artifacts byte-for-byte and must never rebuild Electron or the client installer. A `master` snapshot may publish those exact CI-produced installers before exact-artifact tests finish; a stable `v*` tag must not publish until those tests and the full gate succeed.
- There is exactly one user-facing installer per platform: `xdrive-linux-amd64.deb` on Linux and `xDriveSetup-amd64.exe` on Windows. Do not reintroduce `xdrive-desktop-linux-amd64.deb`, `xDriveDesktopSetup-amd64.exe`, or a second Linux client installer filename.
- Release jobs should not rerun test suites that are already part of full CI. Server images follow **Build Once / Publish Exact Image**, with exact-image/full-suite validation required before stable promotion: `server-image`, `web`, and `caddy-image` build versioned candidate images and persist exact image artifacts; `server-backup` imports the exact server image instead of rebuilding it; release publication imports those same image artifacts, pushes immutable registry tags, and promotes them to `edge` for `master` or `latest` for a stable tag. A `master` snapshot may promote the exact CI-produced images before the remaining full-suite validation completes; a stable `v*` tag must wait for `final-gate`. The publish phase may build deployment assets, but it must not rebuild client installers or server images.
- GitHub `.github/workflows/release.yml` and GitLab `infra/ci/gitlab-release.yml` implement the same split release contract. A `master` push builds publishable installers/images in parallel with full CI and publishes the rolling `snapshot`/`edge` channel as soon as those exact artifacts pass fast publication-integrity checks; ordinary and exact-artifact tests continue independently and do not block the snapshot. A stable `v*` tag still requires the complete `final-gate` before any release publication or `latest` promotion. GitHub invokes the reusable publish workflow from the same CI run so it downloads exact artifacts without rebuilding. GitLab uses DAG `needs`/`rules:needs` so `master` publication can run ahead of the verify stage while stable tags remain gated.
- Release-grade GitHub and GitLab builds must publish the same named file set, use the same release/desktop version semantics, generate `SHA256SUMS.txt`, and publish the same three exact CI-produced server images. Within one provider pipeline, published client installer bytes and server image IDs must come from artifacts produced by that same pipeline. For stable `v*` tags those exact artifacts must be validated by the full gate before publication; for `master`, the same validation may complete after the rolling snapshot has already been published. The two providers may still produce different binary hashes or image IDs because their build hosts, signing environments, timestamps, and Docker builders differ.
- GitLab keeps release-job artifacts for 14 days for pipeline access, but durable release files are uploaded to the GitLab Generic Package Registry and attached to the GitLab Release. Do not use expiring job-artifact URLs as the long-term release source.
- When adding a release file, update the producer copy/chmod steps, the GitLab `release-assets` artifact paths, each provider's publisher input list, and the checksum manifest together; keep the parity contract test explicit enough to fail when any handoff omits the file.
- The server installer supports both registries. GitHub release artifacts bake `ghcr.io/<owner>` as the default image registry; GitLab release artifacts bake `$CI_REGISTRY_IMAGE`. At runtime, `XD_IMAGE_REGISTRY` overrides either default. Do not implement silent cross-registry failover.
- Release baking globally replaces the installer template's `@...@` values. Runtime template detection must use structural placeholder recognition rather than comparing against raw placeholder literals, because those comparison literals would be replaced too. Keep a regression test that executes a fully baked GitLab installer without explicit source/channel flags.
- GitLab 17.x job tokens cannot move repository tags. The rolling GitLab `snapshot` Release must publish `XDRIVE_RELEASE_COMMIT=<full SHA>` in its description, and both Desktop and Server update resolution must treat that validated marker—not the immutable Release tag target—as the authoritative master snapshot commit.
- GitLab `master` snapshot publication runs only when the instance exposes a non-empty `CI_REGISTRY_IMAGE`. On an instance without Container Registry, skip the GitLab release-build/promote/release jobs while the full CI continues normally. Stable `v*` tags must still enter the publication path, wait for the complete gate, and fail clearly when the required registry is unavailable; never invent a registry URL or fall back to another provider.
- Stable `v*` Windows releases require `XD_WINDOWS_SIGN_PFX_B64` and `XD_WINDOWS_SIGN_PFX_PASSWORD` during the CI artifact build on both providers. Master snapshots may be unsigned when those secrets are unavailable; the publish phase must never add or change a client signature because that would change the tested artifact bytes.
- Stable formal releases are cut from `v*` tags. Do not introduce `release/*` as a publication trigger unless the project explicitly adopts a separate stabilization-branch workflow; `master` remains the rolling snapshot/edge channel.

## GitHub / GitLab CI parity

- `.github/workflows/ci.yml` and `.gitlab-ci.yml` are two front ends for the same CI contract. Any change to CI jobs, platform coverage, toolchain versions, test/build commands, Docker/deployment validation, trigger semantics, or merge gates must update both files in the same code change.
- Keep these jobs one-to-one across both systems: `single-commit`, `desktop-linux`, `desktop-windows`, `go-linux`, `go-windows`, and `web`.
- Keep trigger behavior equivalent: GitHub PR-to-`master` corresponds to GitLab MR-to-`master`; pushes to `master` run full CI on both providers but rolling snapshot publication must not wait for that full CI to finish; `v*` tags run full CI and must pass `final-gate` before stable publication on both providers; GitHub `workflow_dispatch` corresponds to a GitLab Web/Run pipeline; GitHub cancel-in-progress corresponds to GitLab interruptible auto-cancel.
- `internal/cicontract/ci_parity_test.go` is the executable parity guard. It parses both YAML files, requires the same job set and key commands, and is part of the normal Go test suites. Do not weaken or bypass it to make one CI provider diverge.
- GitLab jobs use the same literal runner tags as the established GitLab runner setup: `linux` for Linux jobs and `windows` for Windows jobs. Do not indirect these tags through CI/CD variables unless the runner topology itself changes.
- GitLab Linux jobs must run in explicit Docker images, following the same pattern as the established GitLab project. Centralize image names and pinned Linux tool versions in `infra/ci/images.yml`; do not fall back to tools installed on the Linux runner host.
- The `linux` runner must use the Docker executor (or an equivalent container executor that honors GitLab's `image:` keyword). It must be x86_64 and provide access to a Docker daemon for jobs that execute `docker build`, `docker run`, or `docker compose`. With Docker socket binding, mount `/var/run/docker.sock` into job containers; an explicitly configured DinD endpoint is also acceptable. The job image provides Go/Node/Docker CLI tooling; the runner host should not be treated as the toolchain.
- The `go-linux` job uses a resource group because deployment tests intentionally exercise real Docker resources. `single-commit` and `go-linux` use the Go CI image; `desktop-linux` and `web` use the Node CI image. Windows jobs intentionally have no Linux `image:` and continue on the `windows` runner.
- Database integration tests in GitLab `go-linux` must use the GitLab PostgreSQL service alias (`postgres:5432`). Do not start PostgreSQL through the bound Docker socket and publish it to `127.0.0.1`: the Docker daemon host and the Docker-executor job container have different loopback namespaces, so host-published localhost ports are not a valid service endpoint for the job container.
- Electron packaging commands must pass `--publish never` in normal CI/build scripts; publishing is handled by the repository release workflow, not implicitly by electron-builder. GitLab uses `ELECTRON_MIRROR` and `ELECTRON_BUILDER_BINARIES_MIRROR` from `infra/ci/images.yml` for release-asset downloads, and Linux Electron/builder binary caches live under `$CI_PROJECT_DIR/.cache`. These mirror variables may be overridden by GitLab project/group CI/CD variables when an internal mirror is available.
- GitLab CI defaults to mainland-China-friendly dependency endpoints: `GOPROXY` falls back from goproxy.cn to Aliyun, then proxy.golang.org and direct on any error; `GOSUMDB=sum.golang.google.cn` preserves Go checksum verification; Node binaries prefer Huawei Cloud; Docker CLI prefers Aliyun; npm uses npmmirror. Official sources remain fallbacks. `HTTPS_PROXY`/`HTTP_PROXY` are honored normally, and `XDRIVE_CI_GITHUB_RELEASE_PROXY` may prefix GitHub Release downloads when an organization-approved proxy is available.
- Large CI tool downloads must use `scripts/ci/download-with-fallback.sh` so interrupted downloads resume, retry, and fall back between mirrors. Partial tool downloads and Go/npm caches live under `$CI_PROJECT_DIR/.cache`; GitLab caches them with `when: always` so a failed pipeline can resume on the same runner instead of restarting from zero.
- Go 1.25 is the minimum supported toolchain baseline. Canonical module-tidiness validation must run under an actual Go 1.25 toolchain (GitHub Go jobs and GitLab `go-linux`). Self-hosted GitLab Windows runners may use newer Go versions, but they must not run `go mod tidy`: use the committed module graph with `go mod download`, `go mod verify`, and `-mod=readonly` for tests/builds so a newer Go release cannot silently upgrade dependencies or raise their minimum Go requirement.
- Windows CI and upgrade tests must resolve the Inno Setup uninstaller from the xDrive uninstall registry entry's `UninstallString`; never assume the filename is `unins000.exe`, because Inno Setup may allocate `unins001.exe` or later names on persistent runners.
- Windows CI, installer, upgrade, rollback, and legacy-cleanup scripts must only stop xDrive processes in the script's own Windows session. A service runner must never terminate an interactive user's Desktop or Agent merely because the executable name matches.
- The Electron main process writes lifecycle diagnostics to `%LOCALAPPDATA%\xDrive\desktop.log` on Windows, rotates one 2 MiB backup, and uses a running-session marker to report force termination on the next launch. Keep lifecycle logging free of credentials, request bodies, and server tokens.
- Windows service-runner smoke tests must launch Desktop with isolated `LOCALAPPDATA` and `--user-data-dir`, verify the in-process `window_shown` and `startup_complete` lifecycle checkpoints, and clean up only processes created by that test. Do not use `MainWindowHandle` as the readiness signal because a service runner cannot reliably observe Electron HWNDs.
- The GitLab Windows runner is a Windows Shell executor configured with Bash/Git Bash. GitLab `script:` entries for Windows jobs must therefore be Bash commands; do not place raw PowerShell syntax directly in `.gitlab-ci.yml`. Use Bash wrapper scripts and invoke `powershell.exe` explicitly only for Windows-native operations such as certificate creation, Authenticode validation, registry checks, and installer smoke tests. The runner must provide Go >= 1.25, Node.js 22, npm, Git Bash, Windows PowerShell, Chocolatey, Windows CfAPI support, certificate creation/signing support, and permission to install/use Inno Setup.
- GitLab Windows jobs keep Go's module cache under `$CI_PROJECT_DIR/.cache/go-mod`, but GitLab must cache only `$GOMODCACHE/cache/download` rather than the extracted module tree. The extracted tree is read-only and may not survive cache archive/restore byte-for-byte. `default.hooks.pre_get_sources_script` removes the previous worktree copy before Git clean/fetch, then `scripts/ci/prepare-go-mod-cache.sh` verifies the restored download cache and automatically clears/redownloads it if verification fails. Bump the Windows Go/release cache-key version whenever this cache format changes. Do not replace this with a broad `GIT_CLEAN_FLAGS` exclusion for `.cache`, because persistent Shell-runner worktrees must not bypass GitLab cache isolation.

## Master protection

- Never force-push `master` or rewrite its published history.
- Never use `git push --force`, `git push -f`, or `git push --force-with-lease` against `master`.
- Repository branch protection/rulesets for `master` must keep force pushes and branch deletion disabled.
- GitHub changes must arrive through a tested short-lived branch/PR; do not bypass required CI checks. GitLab changes follow the explicitly allowed locally validated direct-to-`master` workflow above.
- Force-pushing a work branch is allowed only when needed to amend/rebase while preserving the branch's single-work-commit invariant, and only after verifying the target is not `master`. Do not accumulate multiple commits and use a late squash as the normal workflow.

Do not merge known failing or untested changes into `master`.

When multiple related unmerged branches exist, prefer dependency order. Dependent follow-on work may continue directly from the upstream work branch without waiting for its PR/MR to merge. Unrelated branches and PRs/MRs are outside the current task's workflow and must not block or reorder the work unless they create a real conflict or alter a required dependency. A dependent branch must contain exactly one work commit above its immediate dependency throughout development. Before it is made merge-ready after the dependency lands, rebase/reconstruct that same single commit onto the latest `master`, keep only its own delta, and require its own PR/MR CI to pass. Avoid rebasing or amending an already-green PR solely to create another CI run.

Prefer small, focused branches that remain single-commit from their first commit through merge, minimizing conflicts, avoiding late-squash CI churn, and keeping `master` history reviewable.
